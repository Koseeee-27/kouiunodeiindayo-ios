# Git 運用ルール

ハッカソン用の軽量ルール。スピードと「壊さないこと」の両立を優先する。

## タスク（GitHub の Issues）

- 開発タスクの正は GitHub の Issues。Notion のタスク管理には、Issue の URL を貼るだけにする（同じ内容を2か所に書かない）
- Issue は、テンプレート（機能の実装／バグ／作業）から作る。優先度のラベル（`MVP`／`デモまで`／`余裕があれば`）は `docs/requirements.md` の優先度に合わせる
- 自分がやる Issue には、自分を担当（Assignees）に入れてから始める。2人が同じものを作らないため
- カメラ・スワイプの手触り・効果音・写真の保存に関わる Issue には、`実機確認が要る` のラベルを付ける

## ブランチ

- **main に直接 push できない**（GitHub 側の設定で禁止している。管理者も同じ）。main は常に動く状態を保つ
- 作業は必ずブランチを切ってから始める。**1ブランチ = 1 Issue**
- 短命ブランチで運用する。長くても1日以内にマージし、長生きさせない

### 命名規則

`<種別>/<Issue番号>-<内容を英語の小文字とハイフンで>`（Issue が無い小さな修正は、番号を省く）

| 種別 | 用途 | 例 |
|---|---|---|
| `feat/` | 機能追加 | `feat/12-sort-swipe` |
| `fix/` | バグ修正 | `fix/34-thumbnail-crash` |
| `docs/` | ドキュメントのみの変更 | `docs/data-model` |
| `chore/` | 設定などの変更 | `chore/xcconfig` |

## マージ（PR）

- マージは **PR 経由のみ**。PR はテンプレートに沿って書き、説明に `Closes #Issue番号` を入れる（マージすると Issue が自動で閉じる）
- PR を作ると、GitHub Copilot が自動でレビューする（push するたびに再レビュー）。指摘を読んで、直すか、直さない理由を返してからマージする。人の承認は必須ではなく、**セルフマージ可**
- マージ方法は squash merge だけ（PR の中のコミットを1つにまとめて main に入れる。GitHub 側でほかの方法は選べない）。main の履歴には PR の題名が残るので、**PR の題名は日本語で、何をしたかが分かるように書く**
- マージしたブランチは GitHub 側で自動で消える。手元のブランチは `git switch main && git pull && git branch -d <ブランチ名>` で片付ける。同じブランチで作業を続けない
- main が進んで PR が古くなったら、PR の画面の「Update branch」で main を取り込める
- **ビルドが通らない PR はマージしない**。エラーは修正してから
- **force push やチェックのスキップで誤魔化さない**。落ちた原因を直す
- `project.pbxproj` が変わっている PR は、なぜ変わったかを PR の説明に書く（ビルド設定の変更など、人が Xcode で行った変更だけのはず）

## コミット

- メッセージは日本語で簡潔に（例: `仕分け画面のスワイプを追加`, `ホームのレイアウト調整`）
- 1コミット = 1つのまとまった変更。動く単位でコミットする
- **AI の署名を付けない**。`Co-Authored-By: Claude ...` や `Generated with Claude Code` 等のトレーラーをコミットメッセージ・PR に含めない
- 生成物・シークレット（APIキー）・個人の署名設定（`Config/Local.xcconfig`）はコミットしない

## push の前に

- **壊れた状態で push しない**。`docs/rules/verification.md` の手順を通してから push する

## pull

- 作業を始める前・区切りごとに必ず pull する
- `AGENTS.md` や `docs/rules/` の変更も pull で反映される。AI ツールの設定変更は次のセッションから有効になる
